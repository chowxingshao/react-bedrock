# Internationalisation (i18n)

The app uses i18next and react-i18next, with translations bundled into the build. Bundled locales: `en` (source of truth) and `es`.

## Where things live

| Path                                          | What                                                                                                                                                          |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/locales/<locale>/<file>.json`            | Translations, one file per namespace. `en` defines the keys. A kebab-case file name is the camelCase namespace: `purchase-orders.json` holds `purchaseOrders` |
| `src/core/i18n/resources.ts`                  | Registers every locale × namespace                                                                                                                            |
| `src/core/i18n/i18next.d.ts`                  | Typed keys: an unknown key fails `pnpm typecheck`                                                                                                             |
| `src/core/i18n/i18n.ts`                       | i18next initialisation, `changeLocale`, `<html>` and formatter sync                                                                                           |
| `src/core/i18n/detect.ts`                     | Language detection (saved, browser, default)                                                                                                                  |
| `src/core/i18n/zod-error-map.ts`              | Translated Zod messages                                                                                                                                       |
| `src/lib/format.ts`                           | Locale-aware date, currency and number formatting                                                                                                             |
| `src/lib/format-locale.ts`                    | The language the formatters use (kept apart so date-fns stays out of the eager graph)                                                                         |
| `src/components/layout/language-switcher.tsx` | The language menu (`Header` and `AuthLayout` mount it)                                                                                                        |

## Using translations

```tsx
import { useTranslation } from 'react-i18next';

const { t } = useTranslation(); // default namespace: common
t('actions.close');

const { t: tItems } = useTranslation('items'); // a feature namespace
tItems('list.title');
t('items:list.title'); // or use a namespace prefix
```

Never write user-facing text directly in JSX: ESLint (`react/jsx-no-literals`) rejects text children. It does not check attribute strings, so translate `aria-label`, `title`, `placeholder` and `alt` yourself.

## Adding a key

1. Add it to `src/locales/en/<namespace>.json`.
2. Add the translation to every other locale. `pnpm typecheck` fails while a locale is missing a key, and `pnpm test` fails while locales have different keys or empty values.

## Namespaces

- `common`: shared UI text (actions, status, pagination, theme, …)
- `errors`: user-facing error messages, including one per backend error code (`errors:codes.<CODE>`)
- `validation`: form validation messages and `validation:server.<CODE>`
- one namespace per feature, added together with the feature (`items` for the reference feature). `pnpm gen feature` does it (docs/generators.md); by hand, import the feature's file of every locale in `resources.ts` and add it to each locale's block, above that block's `plop:resources-<code>` line

## Language detection and switching

The language is detected once, when the app loads. Order (spec §7.6):

1. the saved choice (`locale` under your storage prefix, `react-bedrock:locale` by default; the prefix comes from `VITE_APP_NAME`)
2. the first of the browser's `navigator.languages` that matches a bundled language (a regional tag such as `es-MX` matches `es`)
3. `VITE_DEFAULT_LOCALE`

A saved value that is not a bundled locale is ignored.

`<LanguageSwitcher />` (`@/components/layout`) calls `changeLocale(locale)` from `@/core/i18n`, which switches the language and saves the choice. `Header` and the login page (`AuthLayout`) mount it. Calling `i18n.changeLanguage` directly switches too, but does not save the choice.

On every change:

- `<html lang>` / `dir` update
- the formatters follow
- the HTTP client sends the new `Accept-Language`, on requests made from then on. Query data a backend already localised stays in the old language until it is fetched again, so invalidate those queries if your backend localises content

## Formatting (`@/lib/format`)

| Helper                    | Example (en)                                                        |
| ------------------------- | ------------------------------------------------------------------- |
| `formatDate(iso)`         | Jan 5, 2026                                                         |
| `formatDateTime(iso)`     | Jan 5, 2026, 10:00 AM                                               |
| `formatISODate(date)`     | 2026-01-05 (the local calendar day, for APIs)                       |
| `formatRelative(iso)`     | 3 days ago                                                          |
| `formatCurrency(1234.5)`  | $1,234.50 (currency from `VITE_DEFAULT_CURRENCY`, `USD` by default) |
| `formatNumber(1234567.8)` | 1,234,567.8                                                         |
| `formatPercent(0.256)`    | 25.6%                                                               |

The date examples use `iso` = `2026-01-05T10:00:00Z`, shown in a UTC time zone, with `formatRelative` measured from three days later (its `base` option defaults to now). In `es`, `formatDate(iso)` gives `5 ene 2026`.

- All helpers follow the UI language, or take `{ locale }`. `formatCurrency` also takes `{ currency }`, `formatNumber` accepts any `Intl.NumberFormat` option, and `formatPercent` takes `{ maximumFractionDigits }`. The date helpers return an empty string for an invalid date.
- Dates are shown in the browser's time zone. `parseISO` reads a date-only string such as `2026-01-05` as local midnight, but an ISO string with `Z` (`2026-01-05T10:00:00Z`) as UTC.
- Send a date-only value, such as a DatePicker's, with `formatISODate(date)`, not `toISOString()` or `JSON.stringify`. The picker returns local midnight, and `toISOString()` of that is the previous day east of UTC (`2026-01-04T16:00:00.000Z` for UTC+8). `formatISODate` reads the local date parts and gives `''` for an invalid date.
- `getDateFnsLocale()` returns the date-fns locale for the current language (the DatePicker passes it to the calendar).
- Never import `date-fns` directly (ESLint enforces this).
- Call the formatters in components that use `useTranslation()`, so they re-render when the language changes.

## Validation messages

Zod messages are translated through the `validation` namespace (docs/forms.md). For server field errors, `applyServerErrors` translates known codes from `validation:server.<CODE>`.

## Keys built at runtime

Typed `t('…')` covers every key you write in code. For keys that come from data, such as backend error codes, use `translateKey(key)` from `@/core/i18n`, which returns `undefined` when no translation exists. Never pass it raw server text: use only codes that match `UPPER_SNAKE_CASE` (as `getErrorMessage` and `applyServerErrors` do), because a key such as `constructor` would otherwise resolve to something that is not a string.

## Missing keys

In development a key with no translation, not even in the `en` fallback, logs `Missing translation: <ns>:<key>` once, however often it renders. `translateKey` never logs. The resource test fails when locales have different keys or empty values.

## Adding a language

1. Add the code to `SUPPORTED_LOCALES` in `src/config/constants.ts`.
2. Create `src/locales/<code>/` with a copy of every `en/*.json` file, then translate it.
3. Register it in `src/core/i18n/resources.ts` (import its JSON files, add `const xx: typeof en = { … }`, then add it to `resources`).
4. End that `xx` block with the line `// plop:resources-xx`, where `xx` is the folder name. The generators (docs/generators.md) write one file per folder in `src/locales` and add each new feature's namespace at this line. Without it `pnpm gen feature` refuses to run and says what to add, and `src/test/plop-anchors.guard.test.ts` fails.
5. In `src/lib/format.ts`, import its locale from `date-fns/locale/<code>` and add it to `DATE_FNS_LOCALES`.
6. Add its endonym to `language.names` in every locale's `common.json`.
7. Run `pnpm typecheck && pnpm test`. Missing keys fail both.

`VITE_DEFAULT_LOCALE`, the language switcher and the Storybook Locale toolbar read `SUPPORTED_LOCALES`, so they pick up the new language. The generators need nothing else: files they create for the new language start as copies of the English text. To start from a translation instead, add `plop/templates/feature/locale.<code>.json.hbs` (`locale.es.json.hbs` is the example).

## Removing a language

Undo the steps above: delete `src/locales/<code>/`, its block and imports in `resources.ts` (the `// plop:resources-<code>` line goes with the block), its entry in `SUPPORTED_LOCALES` and `DATE_FNS_LOCALES`, and its endonym in the other locales' `common.json`. The generators then stop writing to it, with no change to `plopfile.js`; delete `plop/templates/feature/locale.<code>.json.hbs` if there is one. `pnpm typecheck` lists what is left, such as unit tests that name the language. At least one locale must stay.

For right-to-left languages `<html dir>` follows `i18n.dir()`. The layout then depends on the utilities you use: prefer logical ones (`ms-*`, `ps-*`, `text-start`) over `ml-*`, `pl-*`, `text-left` in your own components. Some components still use physical utilities. For example, the Sheet primitive has no logical side, so `SheetContent side="left"` (the mobile navigation) stays on the left in a right-to-left language. Check the layout before you ship one.
